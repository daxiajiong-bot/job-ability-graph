# 算法设计：第一阶段 Demo

## 1. 设计目标

第一阶段 Demo 面向“JD 文本 + 简历文本”的单次匹配场景，目标不是训练完整推荐模型，而是形成一套可解释、可落地、可扩展的岗位能力解析与匹配规则。

输入：

1. JD 原始文本
2. 简历原始文本

输出：

1. JD 解析结果
2. 简历解析结果
3. 人岗匹配分数
4. 命中技能
5. 缺失技能
6. 匹配解释
7. 简化岗位-技能图谱

参考 JobFormer 的核心思想：岗位文本本身信息较短且结构化不足，因此需要将 JD 拆成条目级信息，围绕技能分布进行岗位表征，并用技能感知的方式进行匹配与解释。Demo 阶段采用规则 + 词表 + 权重评分实现，后续系统可替换为 JobFormer 式的语义增强表示学习和两阶段召回/排序框架。

## 2. JD 解析规则设计

### 2.1 JD 标准化预处理

对 JD 文本进行统一清洗：

1. 去除多余空格、特殊符号、重复换行；
2. 统一中英文标点；
3. 将项目符号、编号列表转换为条目；
4. 保留原始句子位置，用于后续解释；
5. 对英文技能统一大小写，例如 `python` 归一为 `Python`；
6. 对常见别名做归一化，例如：
   - `PyTorch`、`Pytorch` 统一为 `PyTorch`
   - `JS`、`JavaScript` 统一为 `JavaScript`
   - `大模型`、`LLM`、`Large Language Model` 统一为 `大语言模型`

### 2.2 JD 结构区块识别

将 JD 拆分为以下区块：

| 区块 | 识别关键词 | 作用 |
| --- | --- | --- |
| 岗位名称 | 岗位、职位、招聘职位、Job Title | 判断岗位类型和领域 |
| 岗位职责 | 岗位职责、工作职责、你将负责、Responsibilities | 识别实际工作任务 |
| 任职要求 | 任职要求、岗位要求、能力要求、Requirements | 识别核心能力 |
| 加分项 | 加分项、优先、Bonus、Preferred | 识别非必需能力 |
| 学历要求 | 本科、硕士、博士、学历 | 识别学历门槛 |
| 年限要求 | 年以上、经验、工作年限 | 识别经验门槛 |
| 行业/业务背景 | 金融、医疗、制造、教育、电商等 | 识别领域适配度 |

如果文本没有显式标题，则按语义规则兜底：

1. 出现“负责、参与、建设、设计、开发、维护”等动词的句子归入岗位职责；
2. 出现“熟悉、掌握、精通、具备、有……经验”等句子归入任职要求；
3. 出现“优先、加分、最好、有……者优先”等句子归入加分项。

### 2.3 JD 技能抽取

技能抽取采用“技能词表 + 别名映射 + 上下文规则”。

技能类型分为：

| 类型 | 示例 |
| --- | --- |
| 编程语言 | Python、Java、C++、Go |
| 框架工具 | PyTorch、TensorFlow、Spring Boot、Vue |
| 算法能力 | 机器学习、深度学习、推荐算法、NLP、知识图谱 |
| 数据能力 | SQL、数据分析、数据挖掘、数据仓库 |
| 工程能力 | 系统设计、接口开发、性能优化、分布式系统 |
| 业务能力 | 用户增长、风控、供应链、招聘业务 |
| 通用能力 | 沟通协作、项目管理、文档能力、学习能力 |

每个技能保存以下字段：

```text
skill_name: 标准技能名称
skill_type: 技能类型
source_section: 来源区块
evidence_text: 原文证据
requirement_level: required / preferred / implicit
importance_weight: 技能权重
```

### 2.4 JD 技能权重规则

技能权重用于表示 JD 对该技能的需求强度。

基础权重：

| 来源 | 权重 |
| --- | ---: |
| 任职要求 | 1.0 |
| 岗位职责 | 0.8 |
| 岗位名称 | 0.9 |
| 加分项 | 0.4 |
| 通用软技能 | 0.3 |

强度修正：

| 表达 | 修正 |
| --- | ---: |
| 精通、深入掌握、专家级 | +0.3 |
| 熟练、熟悉、具备经验 | +0.2 |
| 了解、接触过 | -0.2 |
| 优先、加分 | -0.4 |
| 多次出现 | 每次 +0.1，最高 +0.3 |

最终权重：

```text
JD_skill_weight = min(1.5, base_weight + intensity_bonus + frequency_bonus)
```

### 2.5 JD 解析输出结构

JD 解析结果建议包含：

```text
job_title: 岗位名称
job_category: 岗位类别
responsibilities: 岗位职责条目
requirements: 任职要求条目
preferred: 加分项条目
education_requirement: 学历要求
experience_requirement: 年限要求
domain_requirement: 行业/业务背景
skills: 技能列表
skill_distribution: 技能权重分布
```

## 3. 简历解析规则设计

### 3.1 简历标准化预处理

对简历文本进行清洗和结构化：

1. 统一换行、空格、编号；
2. 保留段落标题；
3. 识别时间表达，例如 `2020.07-2023.05`；
4. 识别项目经历、工作经历、教育经历、技能清单；
5. 将技能别名映射为标准技能名称。

### 3.2 简历结构区块识别

| 区块 | 识别关键词 |
| --- | --- |
| 基本信息 | 姓名、电话、邮箱、所在地 |
| 求职意向 | 目标岗位、期望职位 |
| 教育经历 | 教育背景、毕业院校、专业 |
| 工作经历 | 工作经历、实习经历、任职公司 |
| 项目经历 | 项目经验、项目介绍、项目职责 |
| 技能清单 | 专业技能、技能栈、掌握技能 |
| 证书/成果 | 证书、论文、专利、竞赛、开源 |

### 3.3 简历技能抽取

简历技能来源分为显式技能和隐式技能。

显式技能：

1. 来自“专业技能/技能栈”区块；
2. 例如“熟悉 Python、PyTorch、机器学习”。

隐式技能：

1. 来自项目经历、工作经历中的动作和任务；
2. 例如“负责推荐系统召回模型优化”可推断：
   - 推荐算法
   - 召回模型
   - 模型优化
   - 机器学习

每个技能保存：

```text
skill_name: 标准技能名称
skill_type: 技能类型
source_section: 来源区块
evidence_text: 原文证据
proficiency_level: 0-1 熟练度
confidence: 0-1 抽取置信度
recency: 最近使用程度
```

### 3.4 简历技能熟练度规则

基础熟练度：

| 表达 | 熟练度 |
| --- | ---: |
| 精通、主导、架构、负责人 | 1.0 |
| 熟练、独立完成、核心开发 | 0.8 |
| 熟悉、参与开发、具备经验 | 0.6 |
| 了解、接触、学习过 | 0.3 |

来源修正：

| 来源 | 修正 |
| --- | ---: |
| 工作经历中使用 | +0.2 |
| 项目经历中使用 | +0.15 |
| 技能清单中出现但无项目支撑 | -0.1 |
| 证书、论文、竞赛支撑 | +0.1 |

时间修正：

| 最近使用时间 | 修正 |
| --- | ---: |
| 1 年内 | +0.1 |
| 1-3 年 | 0 |
| 3 年以上 | -0.1 |

最终熟练度：

```text
resume_skill_score = clamp(base_level + source_bonus + recency_bonus, 0, 1)
```

## 4. 人岗匹配评分公式

### 4.1 总体评分

Demo 阶段采用 100 分制：

```text
FinalScore =
100 * (
  0.50 * SkillCoverage
+ 0.20 * SkillDistributionSimilarity
+ 0.10 * ExperienceFit
+ 0.08 * EducationFit
+ 0.07 * DomainFit
+ 0.05 * SemanticFit
) - HardPenalty
```

其中：

| 指标 | 含义 |
| --- | --- |
| SkillCoverage | JD 核心技能被简历覆盖的程度 |
| SkillDistributionSimilarity | JD 技能分布与简历技能分布的相似度 |
| ExperienceFit | 工作年限是否满足 |
| EducationFit | 学历是否满足 |
| DomainFit | 行业/业务背景是否匹配 |
| SemanticFit | JD 职责与简历经历的语义相似度 |
| HardPenalty | 硬性条件不满足的扣分 |

### 4.2 技能覆盖率

设 JD 技能集合为 `J`，简历技能集合为 `R`。

```text
SkillCoverage =
sum(weight_jd(skill) * match_score(skill)) / sum(weight_jd(skill))
```

其中：

```text
match_score(skill) =
1.0  简历中明确命中且熟练度满足
0.7  简历中命中但熟练度略低
0.5  简历中存在相关上位/下位技能
0.0  未命中
```

示例：

1. JD 要求 `深度学习`，简历有 `PyTorch、CNN、模型训练`，可给 0.7-1.0；
2. JD 要求 `知识图谱`，简历只有 `NLP`，可给 0.3-0.5；
3. JD 要求 `Java`，简历只有 `Python`，通常给 0。

### 4.3 技能分布相似度

参考 JobFormer 的技能感知思想，将 JD 和简历都转为技能权重分布：

```text
JD_vector = [w1, w2, ..., wn]
Resume_vector = [p1, p2, ..., pn]
```

采用余弦相似度：

```text
SkillDistributionSimilarity =
cosine(JD_vector, Resume_vector)
```

该指标用于衡量整体能力画像是否相似，而不只看单个技能是否命中。

### 4.4 经验匹配

```text
ExperienceFit =
1.0  简历年限 >= JD 要求年限
0.8  相差不超过 1 年
0.5  相差 1-2 年
0.2  明显不足
```

若 JD 无明确年限要求，则默认 `ExperienceFit = 0.8`。

### 4.5 学历匹配

```text
EducationFit =
1.0  满足或高于要求
0.7  略低但经验/项目强
0.3  明显不满足
0.8  JD 未声明学历要求
```

### 4.6 领域匹配

根据行业关键词和项目背景判断：

```text
DomainFit =
1.0  行业背景高度一致
0.7  业务场景相近
0.4  技术相近但行业不同
0.2  无明显相关背景
```

### 4.7 语义匹配

语义匹配用于比较：

1. JD 岗位职责
2. 简历工作经历/项目经历

Demo 阶段可采用关键词重合、任务动词重合和技能上下文相似度。

示例：

JD：

```text
负责推荐算法模型优化
```

简历：

```text
参与推荐系统召回模型迭代，优化点击率
```

可判断为高语义匹配。

### 4.8 硬性扣分

硬性条件包括：

1. 必须技能完全缺失；
2. 学历硬门槛不满足；
3. 年限差距过大；
4. 岗位方向严重不一致。

扣分规则：

```text
HardPenalty =
20  核心必备技能缺失 2 个及以上
15  年限严重不足
10  学历硬门槛不满足
10  岗位方向明显不一致
```

最终分数限制在 `[0, 100]`。

## 5. 技能差距分析规则

### 5.1 命中技能

命中技能满足：

1. JD 中出现；
2. 简历中直接出现或可通过项目经历推断；
3. 技能标准化后名称一致，或属于可接受的同义/上下位关系。

输出字段：

```text
skill_name
jd_weight
resume_proficiency
match_type: exact / alias / related / inferred
evidence_from_jd
evidence_from_resume
```

### 5.2 缺失技能

缺失技能满足：

1. JD 中权重较高；
2. 简历中没有直接或间接证据；
3. 不是纯加分项。

缺失技能按优先级排序：

```text
gap_priority = jd_skill_weight * requirement_importance
```

优先级分为：

| 等级 | 条件 |
| --- | --- |
| 高 | 核心技能缺失，来自任职要求或岗位职责 |
| 中 | 重要技能不足，存在相关经验但不充分 |
| 低 | 加分项缺失或低权重技能缺失 |

### 5.3 技能不足

技能不足不是完全缺失，而是熟练度不满足。

示例：

1. JD 要求“精通 Python”
2. 简历写“了解 Python”
3. 判断为“命中但不足”

输出：

```text
skill_name
required_level
resume_level
gap_type: missing / insufficient / related_only
suggestion
```

### 5.4 匹配解释生成

解释由模板生成，保证 Demo 阶段稳定可控。

高匹配解释：

```text
候选人与岗位在 Python、机器学习、深度学习等核心技能上匹配度较高，且项目经历中存在模型训练和算法优化相关证据，因此技能覆盖率较高。
```

中匹配解释：

```text
候选人具备部分核心技能，如 Python 和数据分析，但在知识图谱、推荐算法等岗位重点能力上证据不足，因此整体匹配度中等。
```

低匹配解释：

```text
岗位要求集中在后端开发和分布式系统能力，但简历主要体现数据分析经历，核心技能覆盖不足，因此匹配度较低。
```

## 6. 简化岗位-技能图谱构建逻辑

### 6.1 图谱节点

Demo 阶段构建轻量级图谱，节点包括：

| 节点类型 | 示例 |
| --- | --- |
| Job | 算法工程师 |
| Skill | Python、机器学习、知识图谱 |
| SkillType | 编程语言、算法能力、工程能力 |
| Resume | 候选人简历 |
| Evidence | 原文证据句 |

### 6.2 图谱边

| 边类型 | 含义 |
| --- | --- |
| Job - requires - Skill | 岗位要求某技能 |
| Resume - has - Skill | 简历具备某技能 |
| Skill - belongs_to - SkillType | 技能属于某类别 |
| Skill - related_to - Skill | 技能之间相关 |
| Skill - evidenced_by - Evidence | 技能由文本证据支撑 |
| Resume - matches - Job | 简历与岗位的匹配关系 |

### 6.3 边权重

岗位到技能：

```text
JobSkillEdgeWeight = JD_skill_weight
```

简历到技能：

```text
ResumeSkillEdgeWeight = resume_skill_score
```

匹配边：

```text
ResumeJobEdgeWeight = FinalScore / 100
```

### 6.4 图谱输出示例

```text
Job: 算法工程师
  requires:
    - Python, weight=1.2
    - 机器学习, weight=1.3
    - 深度学习, weight=1.1
    - 知识图谱, weight=0.9

Resume: Candidate_A
  has:
    - Python, proficiency=0.8
    - 机器学习, proficiency=0.7
    - 深度学习, proficiency=0.6

Match:
  score=78
  hit_skills=[Python, 机器学习, 深度学习]
  missing_skills=[知识图谱]
```

### 6.5 Demo 可视化建议

第一阶段图谱无需复杂推理，重点展示：

1. 一个岗位节点；
2. 一个简历节点；
3. 若干技能节点；
4. 命中技能用绿色边；
5. 缺失技能用红色边；
6. 加分技能用灰色边；
7. 边粗细表示权重或熟练度。

## 7. Demo 阶段与后续完整系统的衔接

### 7.1 Demo 阶段定位

Demo 阶段采用规则驱动，重点验证：

1. JD 和简历能否被稳定解析；
2. 技能抽取是否可解释；
3. 匹配分数是否符合直觉；
4. 命中/缺失技能是否能支撑解释；
5. 简化图谱是否能表达岗位、能力和候选人的关系。

Demo 不追求大规模训练和线上推荐性能。

### 7.2 与 JobFormer 思路的衔接

JobFormer 的关键思想包括：

1. JD 按条目建模，而不是简单拼接成长文本；
2. 利用技能分布指导 JD 表征学习；
3. 通过相似 JD 补充单个 JD 的语义不足；
4. 采用召回 + 排序的两阶段推荐框架；
5. 使用注意力权重提供技能层面的解释。

本项目后续系统可逐步升级：

| Demo 阶段 | 完整系统阶段 |
| --- | --- |
| 规则抽取 JD 技能 | 训练 JD 条目级编码器 |
| 手工技能权重 | 学习技能分布预测 |
| 规则匹配评分 | 语义向量 + CTR/匹配模型 |
| 单 JD 单简历匹配 | 大规模岗位/候选人召回 |
| 简化图谱 | 动态岗位-技能-人才知识图谱 |
| 模板解释 | 注意力权重 + 图谱路径解释 |

### 7.3 后续系统扩展方向

后续完整系统建议包括：

1. 技能本体建设

   建立标准技能库、技能别名、上下位关系、相关技能关系。

2. JD 语义增强

   参考 JobFormer，引入相似岗位作为邻居 JD，缓解单个 JD 信息不足问题。

3. 简历能力画像建模

   将简历解析为技能分布、经验分布、行业分布和项目证据。

4. 双塔召回模型

   使用 JD 向量和候选人向量进行大规模初筛。

5. 精排模型

   使用 JD、简历、技能差距、历史交互数据进行深度匹配评分。

6. 动态演化分析

   基于时间维度分析岗位技能需求变化，例如某岗位对大语言模型、知识图谱、数据治理等技能需求的增长趋势。

7. 图谱推理

   从“岗位-技能-项目-行业-人才”关系中发现潜在匹配和能力迁移路径。

## 8. JobFormer 思想参考与可替换模型层设计

### 8.1 设计定位

第一阶段 Demo 不直接训练 JobFormer，也不把 JobFormer 作为必须运行的模型组件。Demo 的重点是先完成可解释、可演示、可调试的人岗匹配闭环：从 JD 和简历中抽取结构化技能，计算匹配分数，输出命中技能、缺失技能和解释证据。

JobFormer 在本项目中的作用是提供后续模型化升级的思想参考，而不是 Demo 阶段的工程依赖。当前规则版需要在输出结构、特征字段和解释形式上尽量贴近后续模型版，使后续从规则匹配平滑过渡到表示学习和深度匹配，而不需要重写上层业务流程。

### 8.2 可借鉴的 JobFormer 思想

本项目主要借鉴 JobFormer 的以下思想：

1. 条目级 JD 表示

   JD 不应只被当作一整段长文本处理，而应拆分为岗位职责、任职要求、加分项、学历年限要求等条目。每个条目保留原文证据、所属区块、技能标签和权重信息。Demo 阶段用规则完成条目拆分，后续模型版可将每个条目编码为语义向量，再聚合为岗位表示。

2. 技能感知表示

   岗位表示需要围绕技能需求组织，而不是只依赖通用文本相似度。Demo 阶段通过技能词表、别名映射、上下位关系和权重分布构造技能画像；模型版可进一步学习 JD 条目与技能之间的关联强度，得到更细粒度的技能感知岗位向量。

3. 技能分布匹配

   人岗匹配不只判断某个技能是否出现，还要比较岗位需求技能分布与候选人能力分布是否一致。Demo 阶段使用规则权重和余弦相似度计算分布相似度；模型版可用训练得到的技能分布预测、岗位向量和简历向量进行联合匹配。

4. 解释性权重

   匹配结果需要说明“为什么匹配”或“为什么不匹配”。Demo 阶段用来源区块、技能权重、命中证据和缺失技能生成解释；模型版可将注意力权重、技能贡献度、图谱路径和证据条目结合起来，形成更可信的解释。

### 8.3 可替换模型层设计

匹配模块设计为可替换的 Matcher 层，上层业务只依赖统一的输入输出语义，不关心内部采用规则还是模型。

| 实现 | 阶段定位 | 核心逻辑 | 优点 | 局限 |
| --- | --- | --- | --- | --- |
| rule_based_matcher | Demo 阶段默认实现 | 技能词表抽取、规则权重、技能覆盖率、分布相似度、硬性扣分、模板解释 | 可控、可解释、无需训练数据、便于快速演示 | 依赖词表和规则，语义泛化能力有限 |
| jobformer_matcher | 后续模型版实现 | 条目级 JD 编码、技能感知表示、技能分布预测、语义向量匹配、解释性权重输出 | 泛化能力更强，可处理隐含技能和复杂语义关系 | 需要训练数据、算力、评估体系和模型服务部署 |

两种实现应保持一致的输入与输出概念：

输入侧保持一致：

1. JD 结构化解析结果；
2. 简历结构化解析结果；
3. 标准技能库、技能别名和技能关系；
4. 条目级原文证据；
5. 学历、年限、行业等结构化条件。

输出侧保持一致：

1. 最终匹配分数；
2. 技能覆盖率或技能匹配贡献；
3. 命中技能；
4. 缺失技能；
5. 技能不足项；
6. 关键证据条目；
7. 可展示的匹配解释；
8. 可写入图谱的岗位、简历、技能和证据关系。

这样设计后，前端展示、图谱构建、能力差距分析和结果解释不需要绑定某一种匹配算法。Demo 阶段可以使用 rule_based_matcher 生成稳定结果，后续只替换 Matcher 内部实现即可接入 jobformer_matcher。

### 8.4 从规则版升级到模型版的路径

后续从 rule_based_matcher 升级到 jobformer_matcher 可分阶段进行：

1. 保留规则版作为基线

   rule_based_matcher 不应在模型版出现后立即删除，而应作为可解释基线、回归测试基线和冷启动兜底策略。模型输出异常、样本不足或置信度较低时，可回退到规则版结果。

2. 积累训练样本

   Demo 阶段输出的 JD 条目、技能标签、简历技能、命中证据、缺失技能和人工调整结果都可以沉淀为训练数据。后续可补充真实投递、面试、录用、岗位收藏、候选人点击等行为数据，形成监督或弱监督样本。

3. 固化统一数据结构

   在规则版阶段就保持条目级 JD、技能分布、证据文本和解释字段的稳定格式。模型版只替换特征生成和评分方式，不改变上层使用的数据契约。

4. 引入语义表示能力

   先用通用文本向量或轻量双塔模型替换 SemanticFit，再逐步引入条目级 JD 编码、技能感知聚合和技能分布预测。这样可以小步验证每个模型组件是否真实提升匹配效果。

5. 增加模型解释输出

   模型版需要输出技能贡献度、条目权重或注意力权重，并映射回原始 JD 和简历证据。解释层仍沿用 Demo 阶段的命中技能、缺失技能和证据句结构，避免模型结果变成不可解释的黑盒分数。

6. 建立评估与灰度机制

   使用规则版结果、人工标注结果和业务反馈共同评估模型版。可先离线比较 rule_based_matcher 与 jobformer_matcher 的分数排序、缺失技能判断和解释一致性，再在系统中灰度切换。

最终目标不是让 JobFormer 替代所有规则，而是形成“规则可解释、模型可泛化、图谱可沉淀”的组合架构：规则层负责冷启动、约束和解释边界，模型层负责语义泛化和排序能力，图谱层负责长期积累岗位、技能和人才关系。

## 9. 第一阶段输出格式建议

Demo 最终输出建议统一为：

```text
jd_parse:
  job_title
  job_category
  responsibilities
  requirements
  skills

resume_parse:
  education
  experience_years
  projects
  skills

match_result:
  final_score
  skill_coverage
  hit_skills
  missing_skills
  insufficient_skills
  explanation

graph:
  nodes
  edges
```

该结构既能支持前端展示，也能平滑扩展到后续图数据库、模型训练和动态演化分析模块。
